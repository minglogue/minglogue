# 홈페이지 글쓰기 시스템 개발 실패 기록

이제 옵시디언이 아니라 홈페이지에서 직접 글을 작성하고, 초안으로 저장한 뒤, 게시 버튼을 누르면 바로 공개되는 시스템을 만들려고 했다.

원했던 최종 구조는 단순했다.

```text
홈페이지에서 작성
→ 클라우드에 초안 저장
→ 휴대폰과 컴퓨터에서 수정
→ 게시하기
→ 홈페이지 글 목록과 상세 페이지에 즉시 반영
```

하지만 실제 개발 과정에서는 기능이 하나의 흐름으로 연결되지 못했다.

## 원했던 것

기존에는 옵시디언에서 Markdown 글을 작성하고 GitHub에 올린 뒤 홈페이지를 다시 배포해야 했다.
이 방식은 안정적이었지만 휴대폰에서 사용하기 어렵고, 글 하나를 게시하기 위해 거쳐야 하는 과정이 많았다.
그래서 다음 기능을 가진 전용 스튜디오를 만들려고 했다. 결론적으로 접근성을 높이려했다.

- 휴대폰과 컴퓨터에서 같은 글 작성
- 비공개 초안 저장
- 작성한 초안 다시 불러오기
- 사진 자동 압축
- Markdown 미리보기
- 게시 버튼으로 즉시 공개
- 기존 글과 새 글을 같은 목록에서 관리
- 모든 콘텐츠를 클라우드에 보관
- 필요할 때 iCloud로 백업

## 구성하려던 기술

글과 사진은 Cloudflare R2에 저장하고, 스튜디오 접근은 Cloudflare Access로 제한하기로 했다.

```
GitHub
└── 홈페이지 코드와 기존 Markdown 글

Cloudflare R2
├── 새 글
├── 초안
└── 사진

Minglogue Studio
├── 글 작성
├── 사진 압축
├── 초안 저장
└── 게시
```

글을 읽는 것은 누구나 가능하지만, 작성과 수정은 내 이메일 계정으로 로그인한 경우에만 가능하도록 구성했다.

## 구현된 것

완전히 실패한 것은 아니었다.
다음 기능은 각각 동작했다.

- Cloudflare Access 이메일 로그인
- R2 버킷 생성
- 비공개 초안과 공개 글 상태 구분
- Markdown 전체 붙여넣기
- 제목과 본문 메타데이터 자동 분리
- 사진 WebP 자동 압축
- R2에 글 저장
- R2에 저장된 글 다시 불러오기
- Markdown 미리보기
- 공개 글 API
- 기존 GitHub 글 fallback

실제로 작성한 글은 R2에 저장됐고 `published` 상태도 정상적으로 기록됐다.

공개 API에서도 해당 글을 정상적으로 확인할 수 있었다.

## 어디서 실패했는가

문제는 개별 기능이 아니라 전체 연결이었다.

```
스튜디오에서 게시하기
→ R2 저장 성공
→ 공개 상태 저장 성공
→ 공개 API 응답 성공
→ 홈페이지 목록 반영 실패
```

글은 게시됐지만 홈페이지 글 목록이 새 글을 읽지 못했다.

### 데이터 읽기 경로가 여러 개로 나뉨

기존 글은 GitHub Markdown에서 읽고, 새 글은 R2에서 읽도록 구성했다.

두 저장소를 동시에 지원하기 위해 fallback 구조를 만들었지만, 홈페이지·공부 목록·일상 목록·스튜디오 목록·상세 페이지가 서로 다른 방식으로 데이터를 읽게 됐다.

```
홈페이지
└── 자체 목록 구현

공부 목록
└── R2 API + GitHub fallback

스튜디오 공개 목록
└── 별도의 R2 조회

상세 페이지
├── 기존 글 렌더러
└── R2 글 전용 렌더러
```

하나의 글 시스템이 아니라 여러 개의 임시 시스템이 생긴 셈이다.

### 미리보기와 실제 글 화면이 달랐음

스튜디오의 미리보기와 홈페이지의 글 상세 화면이 같은 렌더러를 사용하지 않았다.
그 결과 새 글 상세 화면에서는 기존 글에 있던 정보가 빠졌다.

- 작성일 표기
- 읽기 시간
- 작성자
- 기존 글 레이아웃
- 이미지 처리 방식

한쪽을 수정해도 다른 화면에는 자동으로 반영되지 않았다.

### 게시 완료 검증이 부족했음

배포가 성공했다는 사실과 실제 기능이 정상적으로 동작한다는 사실을 구분하지 못했다.

```
빌드 성공 ≠ 게시 성공
배포 성공 ≠ 홈페이지 목록 반영 성공
R2 저장 성공 ≠ 상세 페이지 표시 성공
```

게시 버튼을 누른 뒤 다음 전 과정을 확인했어야 했다.

1. R2에 글이 저장됐는가
2. 상태가 `published`인가
3. 공개 API가 글을 반환하는가
4. 홈페이지 목록에 나타나는가
5. 공부 또는 일상 목록에 나타나는가
6. 글 상세 주소가 열리는가
7. Markdown과 이미지가 정상적으로 표시되는가
8. 다시 스튜디오에서 불러와 수정할 수 있는가

이 검증을 끝까지 수행하지 않은 채 부분적인 결과만 보고 완료됐다고 판단했다.

### 오류를 숨긴 코드

일부 데이터 요청은 실패할 경우 오류를 표시하지 않고 빈 목록을 반환했다.

```
try {
  // R2 글 불러오기
} catch {
  return [];
}
```

페이지는 깨지지 않았지만, 새 글이 왜 나타나지 않는지 확인하기 어려워졌다.
오류가 없는 것처럼 보였지만 실제로는 데이터 연결이 실패하고 있었다.

## 가장 큰 문제

가장 큰 문제는 기술 선택보다 개발 방식이었다.
기능을 하나씩 추가하면서 전체 워크플로우를 매번 다시 확인하지 않았다.
사용자는 하나의 기능을 사용하는 것이 아니라 하나의 흐름을 사용한다.

```
작성
→ 저장
→ 수정
→ 미리보기
→ 게시
→ 목록 확인
→ 상세 글 확인
```

이 흐름 중 하나라도 끊기면 홈페이지 글쓰기 시스템 전체가 실패한 것이다.

## 기존 방식으로 돌아가기로 함

당분간 글 작성은 다시 옵시디언을 중심으로 사용하기로 했다.

```
옵시디언에서 작성
→ Markdown 파일 저장
→ GitHub에 반영
→ 홈페이지 배포
```

과정은 더 많지만 현재로서는 데이터의 위치와 게시 결과가 명확하다.

- Markdown 원본이 파일로 남음
- 사진도 로컬 폴더에서 확인 가능
- Git으로 변경 이력 관리
- 문제가 생기면 이전 버전 복구 가능
- 홈페이지가 읽는 원본이 명확함

R2에 저장된 글은 즉시 삭제하지 않고 복구용으로 보존한다.

## 다시 개발한다면

다시 홈페이지 글쓰기 기능을 만든다면 처음부터 하나의 데이터 구조와 하나의 렌더러를 사용해야 한다.

```
공통 Post 모델
├── 스튜디오 편집기
├── 미리보기
├── 홈페이지 목록
├── 카테고리 목록
└── 글 상세 페이지
```

게시 기능도 단순 저장으로 끝내지 않고 종단 검증이 필요하다.

```
게시 요청
→ R2 저장
→ 저장 결과 재조회
→ 공개 목록 확인
→ 상세 페이지 확인
→ 성공 표시
```

기존 GitHub 글과 R2 글을 동시에 운영하려면 임시 fallback을 여러 화면에 흩어놓는 대신, 서버의 한 계층에서 데이터를 통합해야 한다.

## 이번에 배운 것

### 기능의 성공과 워크플로우의 성공은 다르다

버튼이 동작하고 API가 응답해도 사용자가 원하는 최종 결과가 나오지 않으면 완성된 기능이 아니다.

### 배포 성공은 검증의 시작이다

배포 로그가 성공했다고 해서 실제 화면까지 정상이라는 뜻은 아니다.
배포 이후 사용자의 실제 행동 순서로 확인해야 한다.

### 데이터 원본은 하나여야 한다

GitHub와 R2를 함께 사용할 수는 있지만, 어느 것이 원본인지 명확해야 한다.
원본이 여러 개면 수정·게시·백업·복구 과정이 복잡해진다.

### 미리보기와 실제 화면은 같은 렌더러를 사용해야 한다

미리보기가 실제 게시 화면과 다르면 미리보기의 의미가 없다.

### 실패를 숨기지 말아야 한다

빈 목록으로 대체하는 것보다 어느 단계에서 실패했는지 명확하게 보여주는 편이 낫다.

## 마무리

이번 작업을 통해 글쓰기 시스템은 편집 화면 하나를 만드는 일이 아니라는 것을 알게 됐다.
저장소, 인증, 이미지, 렌더링, 목록, 상세 페이지, 수정, 백업이 하나의 흐름으로 연결돼야 한다.
부분적으로 동작하는 기능을 여러 개 만드는 것보다, 처음부터 끝까지 검증되는 단순한 흐름 하나를 만드는 것이 더 중요하다.
당분간은 옵시디언과 GitHub를 중심으로 안정적으로 글을 관리한다.
그리고 다시 홈페이지 글쓰기 시스템을 개발하게 된다면 기능 개수보다 전체 워크플로우의 일관성과 복구 가능성을 우선한다.
